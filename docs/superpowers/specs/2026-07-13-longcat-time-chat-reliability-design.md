# LongCat 时间与聊天可靠性修复设计

## 目标

1. 线上诊断必须使用明确的北京时间，不能把任一定时配置误认为当前时间。
2. “咪咪在吗”“在嘛，咪咪”等寒暄不经过指令路由，直接进入聊天。
3. 聊天遇到 LongCat 短暂不可用时只重试一次，同时继续占用现有命令锁。

## 设计

`DiagnosticToolbox` 接受可注入的 `now_fn`，默认调用 `src.beijing_time.now`。调度快照同时输出“当前北京时间”和业务日期，各项定时时间仍保留原字段。

`AiMessageBridge` 在确定性指令检查之后识别有限的寒暄模式，包括“在吗/在嘛/在不在”以及带“咪咪”的问候。命中后复用现有 `_launch_chat`，不调用指令路由模型，也不扩展到可能表示系统操作的文本。

`AiChatService` 只捕获 `LongCatUnavailableError` 并立即重试一次；响应格式错误及其他异常不重试。两次均失败时沿用现有失败提示，`finally` 负责释放命令锁。

## 边界

- 不修改日报、净值、调度和企业微信消息去重逻辑。
- 不增加后台线程或独立服务。
- 不对诊断模型的两步调用增加重试。
- 聊天最多两次请求，最坏耗时仍受单次客户端超时约束。

## 验收

- 调度快照包含注入的北京时间，Cookie 检查时间保持独立字段。
- 两种寒暄直接启动聊天，路由器调用次数为零。
- 聊天第一次短暂不可用、第二次成功时返回答案并只保存一次上下文。
- 两次失败时仍返回现有错误并释放命令锁。
- 全量测试、Python 编译和差异检查通过。

# 钱包Plus赎回到账申购确认顺序修复设计

## 背景

生产库中的两笔理财赎回均已确认并完成到账。系统在到账后生成了对应的钱包Plus `manual_purchase` 流水；这两笔钱包申购仍处于 `pending_confirmation`。

钱包Plus允许待确认申购资金实时用于后续转出，因此持仓投影会把待确认钱包申购排在同交易日其他事件之前。问题发生在申购确认时：状态从待确认变为已确认后，它失去该排序优先级并退回按 `created_at` 排序。生产数据中，赎回到账申购是修复脚本补建的，创建时间晚于同日已经发生的转出，于是确认事务重放到转出时出现临时负份额并回滚。组合周期因此无法继续执行后续定投确认和钱包收益计提。

## 目标

- 赎回到账生成的钱包Plus申购在待确认与已确认状态下保持相同的日内事件顺序。
- 不改变负份额校验，不吞掉结算异常。
- 不修改两笔已经确认并结算完成的原始赎回。
- 生产恢复仅处理两笔钱包申购、18号定投和19至20号钱包收益；21号定投在净值与确认日满足前继续保持待确认。

## 方案比较

### 方案A：按经济语义稳定排序（采用）

识别 `created_by == "redemption_settlement"` 且带 `origin_transaction_id` 的钱包Plus申购，把它们视为到账日零点生效的入账事件。排序优先级不依赖交易当前状态，因此从待确认切换到已确认不会移动位置。

优点是修复根因、改动范围小，并保留所有账本不变量。缺点是需要一个针对赎回到账申购的明确排序谓词。

### 方案B：结算任务跳过失败流水继续执行

可以让定投继续确认，但错误的钱包流水会永久积压，并掩盖持仓不变量问题，因此不采用。

### 方案C：直接修改生产交易状态

能够临时解锁18号定投，但代码缺陷仍会复发，而且绕过事务校验，风险最高，因此不采用。

## 代码设计

在 `src/portfolio_positions.py` 中增加一个只负责排序的谓词，判断交易是否为赎回到账生成的钱包Plus申购。持仓投影排序改为：

1. 交易日期；
2. 赎回到账钱包申购优先；
3. 现有待确认钱包申购优先；
4. 创建时间；
5. 交易ID。

赎回到账钱包申购的排序优先级与状态无关。现有 `pending_purchase_is_in_current_position` 仍只决定待确认资金是否进入当前实时持仓，不扩大确认口径。

## 测试设计

新增回归测试复现生产顺序：

1. 钱包存在较小期初余额；
2. 赎回到账钱包申购在账本中创建较晚；
3. 同交易日较早存在大额钱包转出；
4. 待确认状态下实时持仓为正；
5. 调用 `settle_pending` 确认钱包申购；
6. 确认成功，钱包最终余额不变，且不会触发 `negative portfolio shares`。

同时运行钱包持仓、交易、定投、作业测试及除本机缺失Playwright浏览器之外的全量测试。

## 生产恢复与验证

1. 停止 `daily-report.service`，避免备份和补结算期间并发写入。
2. 使用SQLite在线备份接口备份生产数据库，同时备份受影响源码。
3. 部署单个账本排序文件并执行语法检查。
4. 启动服务，让现有幂等结算流程处理积压。
5. 验证两笔钱包申购已确认、18号定投已确认、21号定投未提前确认、19至20号钱包收益已补记。
6. 对比备份前后数据库，仅允许上述交易状态、对应收益流水和两个产品持仓发生预期变化。
7. 确认组合周期不再产生新错误，净值与收益推送恢复。

# 理财看板份额观察时间修复设计

## 背景

理财看板通过 `data/nav_dashboard_state.json` 保存按产品和净值日期去重的收益流水。每条流水的收益为单位净值差乘以当时有效份额。

2026-07-22 发生了以下顺序：

1. 14:10 至 14:12 修改三个产品的持仓份额。
2. 23:30 首次抓取并写入净值日期为 2026-07-22 的收益节点。
3. 企业微信使用当前配置份额，合计收益为 133.48991108 元。
4. 看板使用旧份额，合计收益为 232.02476208 元，多计 98.53485100 元。

现有实现按净值日期和份额事件的自然日期判断份额是否生效。普通份额修改记录为 `include_start=False`，导致同一自然日稍后才出现的净值节点仍然使用旧份额。这与既有设计中的“份额变化仅作用于尚未出现的新净值节点”不一致。

## 目标

- 份额在某个净值节点入账前修改时，该节点使用新份额。
- 份额在某个净值节点入账后修改时，已入账收益保持不变，新份额从下一个新节点开始生效。
- 已经因旧逻辑写错的流水在再次观察同一净值节点时自动纠正。
- 提供显式、幂等的已有流水纠正入口，使修复执行后无需等待下一次官网刷新即可将 2026-07-22 收益重算正确。
- 自动纠正只更新原流水，不新增重复流水，不重复累计收益。
- 企业微信现有净值查询、手工设置看板总收益、产品生命周期和历史累计规则保持不变。

## 非目标

- 不修改企业微信净值计算口径。
- 不手工编辑生产状态 JSON；生产纠正必须调用经过测试的幂等方法，并在执行前单独备份状态文件。
- 不从官网重新抓取或重建全部历史流水；纠正仅基于状态文件中已有流水及其时间戳原地核算。
- 不改变用户通过“设置收益”指令手工覆盖最新日期组合总收益的行为。
- 本地实现和验证不包含生产部署；部署与线上状态核对使用单独的受控流程。

## 方案选择

采用“观察时间语义”：以份额事件的 `changed_at` 和收益流水的 `discovered_at` 判断某条流水应使用的份额。

不采用仅调整 `include_start` 的同日规则，因为净值可能延迟披露，净值日期与实际抓取日期可能不同。仅比较自然日期不能完整表达“节点是否已经出现”。

不采用手工总收益覆盖作为修复，因为它无法纠正产品收益、贡献排行和原始流水。

## 数据模型

不新增状态字段，不升级状态版本。

现有份额事件已经保存：

- `changed_at`：份额事件的北京时间时间戳。
- `shares`：该事件设置的新份额。

现有收益流水已经保存：

- `discovered_at`：该净值节点首次写入看板的北京时间时间戳。
- `shares`：写入流水时使用的份额。
- `delta`：本期单位净值差。
- `amount`：收益金额。

原有 `effective_date` 和 `include_start` 字段继续保留以兼容已有状态文件，但新计算不再依赖这两个字段选择份额。

## 份额选择规则

新增按观察时间选择份额的内部逻辑：

1. 解析目标观察时间。
2. 遍历产品的 `share_events`。
3. 忽略缺少或无法解析 `changed_at` 的事件。
4. 选择 `changed_at <= observed_at` 的最后一个有效事件。
5. 返回该事件的份额；不存在有效事件时返回空，不产生收益流水。

首次初始化时，初始份额事件和历史回溯使用同一个 `discovered_at`，因此初始配置份额仍可用于统计起点后的回溯流水。

## 新流水写入

`NavDashboardStore._record_pair()` 写入新净值节点时：

1. 使用本次 `discovered_at` 选择有效份额。
2. 计算 `amount = delta * shares`。
3. 保存原有流水字段和所用份额。
4. 继续使用产品键和净值日期组成的 ID 去重。

## 已有流水纠正

新增 `NavDashboardStore.reconcile_profit_entries()`，遍历已有产品收益流水，并按每条流水自身的 `discovered_at` 重新选择当时有效份额：

1. 使用现有流水自己的 `discovered_at` 选择当时有效份额。
2. 以现有流水的 `delta` 重新计算收益。
3. 如果份额和金额均相同，不修改该流水。
4. 如果不同，只更新现有流水的 `shares` 和 `amount`，不修改 ID、净值日期、发现时间、净值或差值。
5. 返回被纠正的流水数量；数量为零表示状态已经一致。
6. 只有至少一条流水发生变化时才保存状态文件。

`record_history()` 和 `record_results()` 在正常观察流程中调用同一纠正逻辑，使以后重复观察也能自动自愈。

重复观察某产品同一净值日期时，不新增流水；显式纠正与正常刷新共享同一个计算入口，避免出现两套修复口径。

这会自动修正 2026-07-22 的三条错误流水，因为它们的 `discovered_at` 晚于对应份额事件的 `changed_at`。如果份额事件发生在流水的 `discovered_at` 之后，重复刷新仍会选择旧份额，已入账收益保持不变。

## 异常与兼容处理

- 无法解析流水 `discovered_at` 时不自动改写该流水，并记录警告，避免猜测业务时间。
- 无法解析某个份额事件时跳过该事件，其余事件继续参与选择。
- 金额计算继续使用 `Decimal`，不引入浮点数。
- 状态保存继续使用现有锁、临时文件和 `os.replace()` 原子替换。
- 已有手工日收益覆盖继续在 payload 汇总阶段应用，不参与产品流水纠正。

## 测试设计

在 `tests/test_nav_dashboard.py` 增加以下回归测试：

1. 同日份额修改发生在净值节点入账之前，新节点使用新份额。
2. 份额修改发生在净值节点入账之后，重复观察不修改已入账流水。
3. 构造旧逻辑产生的错误流水，重复观察后原地更新份额和金额，流水数量保持为一。
4. 显式调用 `reconcile_profit_entries()` 可立即修正历史错误流水，第二次调用返回零且不改变状态。
5. 净值日期早于观察日期的延迟披露节点仍按观察时间选择新份额。
6. 初始历史回溯仍使用初始化时的当前份额。
7. 既有“份额变化仅影响未来节点”和收益去重测试继续通过。

验证命令：

```powershell
python -m pytest -q tests/test_nav_dashboard.py
python -m pytest -q
```

## 验收标准

- 复现线上时序时，三个受影响产品分别计算为 21.607146、11.714593 和 1.380834 元。
- 2026-07-22 五个产品合计为 133.48991108 元。
- 修复代码部署后，先备份 `data/nav_dashboard_state.json`，再显式执行一次 `reconcile_profit_entries()`；执行完成后立即读取 payload，`latest_profit` 必须为 `133.48991108`，不能以等待后续定时刷新代替验收。
- 同一流水重复观察不会增加流水数量。
- 入账后修改份额不会回改已入账收益。
- 完整测试集通过。
- 本地实施不修改或上传任何生产数据。

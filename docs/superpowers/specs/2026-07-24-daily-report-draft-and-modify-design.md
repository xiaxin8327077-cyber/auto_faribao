# 日报草稿暂存、追加与提交后修改设计

## 文档状态

- 修订日期：2026-07-29
- 状态：已确认，待编写实施计划
- 范围：企业微信日报草稿、追加、查看、清除，以及当天 OA 日报的追加和覆盖修改

## 背景与现状

当前日报流程为：定时任务或企业微信指令触发 → 检查智能文档 Cookie → 从智能文档提取内容 → 提交到 OA。

现有系统存在以下能力和约束：

1. `src.target.get_previous_report_content()`只读取今天以前的上一条日报，不能用来读取今天的正文。
2. `src.target.get_report_content_by_date()`可以按准确日期读取 OA 日报。
3. `src.target.modify_daily_report()`默认点击表格第一行，未验证该行日期，不能直接用于安全修改今天的日报。
4. 企业微信文本进入指令路由前会压缩全部空白字符，现有流程不能保留多行日报格式。
5. `src.target.submit_daily_report()`在“日报已审核、无法修改”时可能返回成功但实际动作为跳过，不能仅凭布尔成功值清除草稿。
6. AI 写操作的二次确认只覆盖 AI 路由产生的指令，直接发送精确指令会绕过该确认流程。

本设计在现有流程上增加两类能力：

1. 提交前草稿：设置、追加、查看和清除当天草稿，定时或手工提交时优先使用草稿。
2. 提交后修改：准确读取并修改北京时间当天的 OA 日报，支持追加和完整覆盖。

## 目标

- 用户可以通过企业微信保存完整多行日报草稿。
- 用户可以发送“追加日报”，由系统根据今天是否已经提交自动选择追加到 OA 或当天草稿。
- 当天无草稿且未提交时，“追加日报”先读取智能文档生成当天草稿，再追加用户内容。
- 当天已有 OA 日报时，追加和覆盖修改必须经过二次确认。
- 所有 OA 读取和修改必须按北京时间当天的准确日期定位，不能依赖第一行或上一条日报。
- 草稿跨服务重启存活，但不能跨日期自动提交。
- 草稿存在时提交流程不访问智能文档，也不检查智能文档 Cookie。
- 多行正文的换行、编号和空格必须原样保留。
- 并发、重复企微回调、通知失败和服务异常不能造成重复追加、误删草稿或误报成功。
- 保持智能文档提取、理财看板、OA 数据结构和现有 Cookie 续期逻辑不变。

## 非目标

- 不增加日报历史版本管理界面。
- 不允许修改任意历史日期的日报，本期只修改北京时间当天日报。
- 不增加多用户草稿隔离；草稿仍为单业务账号的一份当天草稿。
- 不通过删除后重新提交的方式模拟 OA 修改。
- 不自动重试 OA 修改，避免重复写入。
- 不增加 SQLite 或其他数据库。
- 不增加服务自动重启。

## 方案选择

采用“提交编排层统一决策 + 日期化本地 JSON 草稿 + OA 准确日期修改”。

职责划分如下：

- `src/daily_report_draft.py`只负责草稿的持久化、并发保护、日期和版本校验。
- `src/daily_report_edit_confirmation.py`只负责待确认 OA 修改的保存、取出、取消和超时。
- `src/server.py`负责保留企业微信原始正文、判断今天 OA 状态、选择草稿或 OA 路径，并组织通知。
- `src/target.py`负责准确日期的 OA 读取、修改和修改前内容一致性校验。
- `src/ai_command_router.py`只判断用户意图，不生成、改写或转述日报正文。
- `src/report_builder.py`继续只负责智能文档和上一条日报内容生成，不读取草稿。

不采用以下方案：

- 不在 `report_builder.py` 中读取草稿，避免“读取日报”等普通生成调用被草稿污染。
- 不复用 `get_previous_report_content()`读取今天，避免把昨天正文覆盖到今天。
- 不复用现有“第一行修改”逻辑，避免今天无日报时修改上一条记录。
- 不使用“删除今天日报后重新提交”，避免审核状态变化和先删后写失败。

## 草稿数据模型

草稿固定保存到项目绝对路径：

`<项目根目录>/data/daily_report_draft.json`

文件结构：

```json
{
  "schema_version": 1,
  "report_date": "2026-07-29",
  "content": "一、【项目A】任务名称：描述\n二、【项目B】任务名称：描述",
  "origin": "manual",
  "revision": 3,
  "created_at": "2026-07-29T16:30:00+08:00",
  "updated_at": "2026-07-29T16:45:00+08:00"
}
```

字段规则：

- `schema_version`：固定为 `1`，不识别的版本必须报错。
- `report_date`：草稿所属北京时间日期，格式为 `YYYY-MM-DD`。
- `content`：完整多行正文，不自动重新编号，不压缩换行和空格。
- `origin`：
  - `manual`：用户直接设置的完整草稿。
  - `smart_sheet_append`：智能文档正常提取内容后追加了用户内容。
- `revision`：每次设置或追加递增，用于提交后的条件清除。
- `created_at`、`updated_at`：带 `+08:00` 时区的北京时间。

## 草稿持久化规则

`src/daily_report_draft.py`提供以下接口：

```python
save_draft(report_date, content, origin) -> Draft
append_draft(report_date, content) -> Draft
load_draft() -> Draft | None
load_draft_for_date(report_date) -> Draft | None
clear_draft(expected_report_date=None, expected_revision=None) -> bool
```

处理规则：

1. 使用进程内可重入锁保护读取、写入、追加和清除。
2. 写入时先在同目录创建临时文件，完整写入并刷新后使用原子替换。
3. Linux 上将文件权限设置为仅服务用户可读写。
4. 文件不存在返回 `None`。
5. JSON 损坏、字段缺失或版本不支持时明确抛错，不得当成“没有草稿”。
6. 保存空白正文或追加空白正文必须拒绝。
7. 正文超过 10000 个字符时拒绝并返回实际字符数，不截断保存。
8. 同一天再次“设置日报”时保留原 `created_at`、递增 `revision`并整体覆盖正文。
9. 用户明确“设置日报”时允许用今天的新草稿替换过期草稿；其他自动流程不得覆盖过期草稿。
10. `load_draft_for_date()`发现其他日期的草稿时返回“过期草稿”状态，不能自动删除或用于今天。
11. 过期草稿保留供查看；用户必须清除或重新设置今天草稿。
12. 条件清除必须同时匹配 `report_date` 和 `revision`。提交期间产生的新版本不能被旧提交任务删除。

## 企业微信原始消息解析

企业微信回调必须同时保留：

- `raw_content`：用户原始文本，保留全部换行和空格。
- `normalized_command`：只用于现有普通指令匹配的标准化文本。

新增解析函数：

```python
parse_daily_report_edit_command(raw_content) -> ParsedReportCommand | None
```

解析规则：

1. 精确指令只解析第一行或第一个冒号以前的动作名称。
2. 动作后的剩余原始文本作为正文，不经过 `_normalize_message_text()`。
3. 支持换行、中文冒号和英文冒号三种正文分隔方式。
4. 正文为空时返回明确格式提示。
5. “设置日报提交时间”必须优先精确匹配，不能被“设置日报”截获。
6. 解析日报编辑指令后才进入原有普通指令标准化流程。
7. 查看草稿正文过长时分段发送，不能静默截断。

## 指令语义

| 指令 | 行为 | 是否二次确认 |
|------|------|--------------|
| `设置日报\n[完整内容]` | 今天未提交时覆盖当天草稿；今天已提交时拒绝并提示使用“修改今日日报” | 否 |
| `追加日报\n[追加内容]` | 自动查询今天 OA 状态，已提交则准备追加 OA，未提交则追加或创建当天草稿 | 修改 OA 时是 |
| `追加今日日报\n[追加内容]` | 明确要求追加今天 OA；今天未提交则拒绝并提示使用“追加日报” | 是 |
| `修改今日日报\n[完整内容]` | 完整覆盖今天 OA 日报；今天未提交则拒绝并提示使用“设置日报” | 是 |
| `查看草稿` | 显示草稿所属日期、来源、版本、更新时间和正文 | 否 |
| `清除草稿` | 删除当前保存的草稿，包括过期草稿 | 否 |
| `确认执行` | 执行当前用户尚未过期的 OA 日报修改 | 不适用 |
| `取消执行` | 丢弃当前用户待确认的 OA 日报修改 | 不适用 |

## “追加日报”自动分流

“追加日报”严格按以下顺序处理：

1. 使用 `get_report_content_by_date(cfg, today)`准确查询今天 OA 日报。
2. 查询异常时停止，不猜测为“未提交”，也不修改草稿。
3. 今天 OA 日报存在：
   - 拼接“现有正文 + 一个换行 + 用户追加正文”。
   - 保存待确认修改。
   - 展示目标日期、原正文摘要和修改后完整正文。
4. 今天 OA 日报不存在且有今天草稿：
   - 在锁内追加到草稿。
   - 返回新的版本号和完整草稿。
5. 今天 OA 日报不存在且没有今天草稿：
   - 先检查智能文档 Cookie。
   - 调用现有 `build_report_with_meta()`。
   - 只有来源为正常智能文档且状态正常时才能创建 `smart_sheet_append` 草稿。
   - 智能文档异常、网络异常、Cookie 失效或退回上一条日报时停止，不得用上一条日报创建追加草稿。
6. 存在过期草稿时停止并提示用户先查看、清除或重新设置今天草稿。

## 草稿优先提交

`server.auto_submit_if_needed()`调整为以下顺序：

1. 读取草稿状态。
2. 草稿文件损坏：通知失败并停止。
3. 存在过期草稿：通知用户处理并停止，不提交今天内容。
4. 存在今天有效草稿：
   - 跳过智能文档 Cookie 检查。
   - 跳过 `build_report_with_meta()`。
   - 使用草稿正文提交 OA。
5. 没有草稿：完整沿用现有 Cookie 预检、智能文档提取和上一条日报确认流程。

手工“发送日报”和定时提交必须复用同一个 `auto_submit_if_needed()`流程。

### 草稿清除时机

提交开始时记录草稿的 `report_date` 和 `revision`。

只有同时满足以下条件才清除该版本草稿：

1. OA 返回成功。
2. OA 返回的实际动作是“提交”或“覆盖”，不是“跳过”。
3. 条件清除时磁盘草稿仍是同一日期和版本。

清除动作必须发生在 OA 已确认写入后、发送企微成功通知前。企微通知失败不能导致已提交草稿保留并在下一次重复提交。

可为 `_submit_and_notify()`增加可选的“OA 已实际写入”回调。现有调用方行为保持不变；草稿路径通过回调执行条件清除。

## OA 准确日期修改

修改 `src.target.modify_daily_report()`接口：

```python
modify_daily_report(
    content,
    cfg,
    report_date,
    expected_content_hash=None,
) -> tuple[bool, str, dict]
```

处理规则：

1. 规范化并固定目标日期，本期只允许北京时间今天。
2. 翻页查找准确日期对应的行，不能点击第一行。
3. 找不到目标日期时返回“今天尚未提交日报”，不得操作其他行。
4. 打开目标行后再次读取当前正文。
5. 提供 `expected_content_hash` 时，当前正文哈希不一致必须中止。
6. 只修改目标日报详情，不删除日报、不重建日报。
7. OA 已审核或不允许修改时返回明确失败。
8. 修改提交后重新读取当天正文，只有与目标正文完全一致时才报告成功。
9. 无法完成提交后校验时报告“修改结果未知”，不得自动重试或宣称成功。

## OA 修改二次确认

`src/daily_report_edit_confirmation.py`使用按用户隔离的进程内存储，服务重启后自动失效，不写入磁盘。

待确认结构：

```json
{
  "user_id": "企业微信用户标识",
  "action": "append_today",
  "report_date": "2026-07-29",
  "original_content_hash": "摘要",
  "original_preview": "原正文摘要",
  "final_content": "修改后的完整正文",
  "created_at": 0,
  "expires_at": 0
}
```

规则：

1. 有效期为 120 秒。
2. 每个用户只能保留一个待确认修改，新操作覆盖该用户旧操作。
3. 直接精确指令和 AI 识别指令共用同一确认存储。
4. 确认操作只能消费一次；重复“确认执行”不能再次修改。
5. 确认时重新读取准确日期正文并比较哈希。
6. 正文变化、日期变化、超时、取消或服务重启均停止修改。
7. 执行成功、失败或结果未知后都清除本次待确认操作。
8. 修改后完整正文超过单条企微消息限制时分段展示，确认入口只在全部正文发送完成后给出。

## AI 自然语言识别

AI 路由只返回以下动作，不携带日报正文：

- `设置日报`
- `追加日报`
- `追加今日日报`
- `修改今日日报`
- `查看草稿`
- `清除草稿`

正文处理规则：

1. AI 不得在 `canonical_command` 中复述正文。
2. 正文始终从用户原始消息中确定性提取。
3. 原始消息含换行时，第一行之后为正文。
4. 单行消息含中文或英文冒号时，冒号之后为正文。
5. 无法确定正文边界时返回澄清提示，不得猜测或生成正文。
6. AI 不判断今天是否已经提交；状态分流由服务器查询 OA 后决定。
7. AI 路由产生的 OA 修改与直接指令使用同一二次确认流程。
8. 日报正文不得写入普通日志；日志只记录动作、日期、字符数、版本和必要的内容哈希。

示例：

- “帮我设置今天日报：一、完成项目接口联调” → 动作 `设置日报`，正文取第一个冒号以后。
- “往日报后面加一条：完成生产验证” → 动作 `追加日报`，由服务器查询今天 OA 状态。
- “把今天已提交日报改成：一、修复问题\n二、完成测试” → 动作 `修改今日日报`，保留原始换行并进入二次确认。

## 重复回调和并发

1. 草稿模块使用锁保证设置、追加、读取和条件清除的原子性。
2. 所有 OA 浏览器操作使用现有全局命令锁，所有异常路径必须释放。
3. 对会产生追加或修改的企业微信文本消息按 `MsgId`做有界时效去重。
4. 相同 `MsgId`在有效期内只处理一次，重复回调返回成功但不重复写入。
5. 二次确认对象消费一次，重复确认不重复修改。
6. OA 状态查询和修改确认不能并行覆盖同一用户操作。

## 通知与来源

草稿提交时的来源和智能文档状态：

| 草稿来源 | `report_source` | 智能文档状态 |
|----------|-----------------|----------------|
| 用户完整设置 | `manual` | `not_used` |
| 智能文档后追加 | `smart_sheet_append` | `normal` |

`src/wechat_notifier.py`增加 `smart_sheet_append`的中文来源文案“智能文档加手工追加”，不能显示英文内部值。

成功通知至少包含：

- 目标日期。
- 实际动作：提交、覆盖、追加或修改。
- 内容来源。
- 草稿是否已清除。

失败通知必须区分：

- 草稿损坏。
- 过期草稿。
- OA 查询失败。
- 今天无日报。
- 日报已审核。
- 内容在确认期间发生变化。
- 修改失败。
- 修改结果未知。

## 错误处理原则

- 无法确认状态时停止，不猜测成功或失败。
- 草稿损坏时不覆盖原文件，不自动回退智能文档。
- OA 今日状态查询失败时不当成“未提交”。
- 智能文档异常时不使用上一条日报创建追加草稿。
- OA 修改失败时不假定 OA 内容保持不变，必要时重新读取并报告实际状态。
- 修改结果未知时不自动重试。
- 通知失败和业务写入结果分开记录，通知失败不能改变已确认的 OA 写入结论。
- 所有用户可见成功文案必须来自已验证的磁盘状态或 OA 状态。

- `src/nav_dashboard.py`：理财看板不变。

## 测试设计

### 草稿持久化

- 设置后可读取相同多行正文。
- 追加后换行、编号和空格完全保留。
- 空白正文拒绝保存或追加。
- 超过 10000 个字符的正文拒绝保存，不截断。
- 写入使用绝对路径和原子替换。
- 文件损坏、字段缺失、版本不支持时明确失败。
- 昨日草稿不能作为今日草稿提交。
- 过期草稿保留且可查看、清除。
- 明确设置今天草稿可以替换过期草稿。
- 条件清除只删除相同日期和版本。
- 提交期间追加产生的新版本不被旧提交删除。
- 多线程并发追加不丢失内容。

### 企业微信解析

- 六个日报编辑指令正确识别。
- 多行正文逐字保留。
- 中文冒号和英文冒号后的正文正确保留。
- 缺少正文时返回格式提示。
- “设置日报提交时间”不被“设置日报”截获。
- 普通现有指令仍走原标准化流程。
- 相同 `MsgId`重复回调不重复追加。

### 自动分流

- 今天 OA 已提交时“追加日报”生成待确认 OA 追加。
- 今天未提交且有当天草稿时追加草稿。
- 今天未提交且无草稿时使用正常智能文档生成草稿再追加。
- OA 查询失败时不修改草稿。
- 智能文档异常、Cookie 失效、网络异常或回退上一条日报时不创建追加草稿。
- 存在过期草稿时不创建今天草稿。

### 草稿优先提交

- 有今天草稿时不调用 Cookie 检查和 `build_report_with_meta()`。
- 无草稿时完整沿用现有提交流程。
- 草稿损坏或过期时不提交。
- OA 实际提交后按版本清除草稿。
- OA 返回跳过、已审核或失败时保留草稿。
- 通知失败但 OA 已实际写入时草稿仍正确清除。
- 草稿提交期间产生新版本时保留新版本。

### OA 准确日期修改

- 修改只定位今天记录，不点击第一行。
- 今天记录不在第一页时可以翻页找到。
- 今天无日报时不修改上一条。
- 追加读取今天正文，不读取昨天正文。
- 已审核日报返回失败，不删除重建。
- 确认时正文哈希变化则停止。
- 修改后读取正文完全一致才报告成功。
- 修改后无法验证时报结果未知，不自动重试。

### 二次确认

- 直接指令和 AI 指令都创建相同类型待确认操作。
- 确认消息包含目标日期、原摘要和最终正文。
- 正确用户在 120 秒内确认可执行一次。
- 超时、取消、错误用户和重复确认均不修改。
- 新待确认操作覆盖同一用户旧操作。
- 服务重启后待确认操作自动失效。

### AI 路由

- AI 只返回动作，不在标准指令中携带正文。
- 原始正文不经过模型输出。
- 无明确正文分隔符时要求补充。
- AI 不判断日报是否已提交。
- 现有非日报指令分类不回归。

### 回归

- 现有日报立即发送、定时提交、上一条日报确认、撤回、查询和统计流程通过。
- 现有 Cookie 检查与续期测试通过。
- 理财净值和收益看板测试通过。
- 完整测试集通过。

## 验收标准

- 多行日报正文从企微到草稿、确认和 OA 全链路保持不变形。
- “追加日报”能根据今天 OA 状态正确选择 OA 或草稿路径。
- 任何情况下都不会把昨天日报正文当作今天正文追加。
- 今天无日报时不会修改上一条日报。
- 有当天草稿时提交不依赖智能文档 Cookie。
- 过期草稿不会跨日提交，也不会被系统静默删除。
- OA 实际提交后只清除当时提交的草稿版本。
- 已审核、跳过、失败和结果未知时不误报成功。
- 直接和 AI 触发的 OA 修改都必须二次确认。
- 重复回调、重复确认和并发追加不会产生重复内容。
- 帮助菜单包含所有新指令和准确格式。
- 完整测试集通过。
- 本地提交不包含 `config.yaml`、Cookie、日志、截图、草稿正文或生产数据。

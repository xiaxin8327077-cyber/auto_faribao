# 日报续期与兜底修复设计

## 目标

修复三个相互关联的生产问题：二维码任务结束后指令状态不释放；定时日报提交前不验证 Cookie；智能文档不可用时无法读取已审核历史日报作为兜底。扫码续期成功后，系统自动使用新 Cookie 继续提交当日日报。

## 已确认根因

1. `src.server` 在“生成二维码”入口设置了全局指令忙状态，但异步二维码线程完成、失败或超时后没有调用 `_end_cmd()`。二维码模块自己的 `RENEW_LOCK` 已释放，指令层状态却永久保留。
2. 每日 09:45 的 Cookie 检查在 2026-07-09 当天通过，但 17:56 定时提交前未复检。Cookie 在两次任务之间失效后，系统先执行两轮 90 秒智能文档提取，且 `Page load timeout` 未进入 Cookie 续期分支。
3. 历史日报兜底确实被调用。当前实现未提供日期时不设置截止日期，曾错误读取当天日报；当天日报被重发流程删除后，只剩已审核历史记录。已审核记录的正文位于展开行的 `.el-form-item` 中，“详情”标签与正文视觉分行但 DOM 文本相连，现有按文本行查找“详情”的逻辑因此返回空字符串。
4. 二维码子进程会更新 `config.yaml`，父进程中的 `cfg` 仍保留旧 Cookie。续期成功后的自动续提必须重新加载配置。

## 方案比较

### 方案 A：共享流程内修复（采用）

在二维码异步入口增加完成回调；日报提交入口增加 Cookie 前置检查；续期成功后重新加载配置并单次恢复提交；历史日报解析按 OA 的结构化表单项读取。该方案同时覆盖定时提交、手动“发送日报”和手动“生成二维码”，改动集中且行为一致。

### 方案 B：仅在调度器外层串联

由调度器先检查 Cookie，再调用现有提交函数。改动较少，但手动“发送日报”仍会走旧流程，二维码指令状态和历史兜底仍需另外处理，容易产生两套行为。

### 方案 C：持久化日报工作流状态机

将“待续期、续期中、待恢复、已提交”写入持久化状态，服务重启后也能恢复。可靠性最高，但对当前三个缺陷而言范围过大，暂不采用。

## 处理流程

1. 日报提交开始时调用 `check_cookies(cfg)`。
2. Cookie 有效时，继续现有“智能文档优先、历史日报兜底”流程。
3. Cookie 无效或检查超时时，不读取智能文档、不立即提交历史日报，发送二维码并结束当前提交调用。
4. 二维码成功后，完成回调重新读取 `config.yaml`，跳过重复前置检查，恢复一次当日日报提交。
5. 二维码失败或超时时，不提交日报，并明确通知“续期未完成，当日日报尚未提交”。
6. 所有二维码结束路径都执行完成回调；手动“生成二维码”的回调用于释放全局指令忙状态。
7. 历史兜底默认只允许选择今天之前的记录。展开已审核记录后，优先按 `.el-form-item` 的“详情”标签读取对应内容，再保留原文本策略作为兼容兜底。

## 去重与边界

- 每个续期任务的恢复回调只执行一次。
- 自动恢复使用续期后重新加载的配置，避免旧 Cookie 重试。
- 恢复提交仍沿用现有 OA 当日报告检查与替换逻辑，不改变日报正文生成和通知口径。
- 本次不修改理财净值、Web 看板、日报定时时间或企业微信消息样式。
- 服务若在扫码与恢复提交之间重启，本次不做跨重启恢复；用户会收到续期结果，可再次发送“发送日报”。

## 错误处理

- 二维码线程无论成功、失败、异常或子进程超时，都释放指令状态。
- Cookie 前置检查失败时记录原始错误并在二维码原因中展示，不把该次日报标记为提交成功。
- 续期成功但恢复提交失败时，沿用现有日报失败通知，保留智能文档和兜底错误信息。
- 历史记录存在但正文无法解析时，继续尝试后续候选记录；全部失败后才返回 `No previous report content found`。

## 测试设计

1. 二维码线程成功、失败和抛异常时均调用完成回调，手动指令状态恢复为空闲。
2. Cookie 有效时正常生成并提交日报，不触发二维码。
3. Cookie 失效时不立即提取或提交；二维码成功后重新加载配置并只恢复提交一次。
4. 二维码失败或超时时不恢复提交。
5. 未指定截止日期时，历史兜底排除当天记录。
6. 已审核展开行中“详情”标签和正文位于同一 DOM 文本时，仍能提取完整正文且不混入审核说明、审核时间。
7. 运行全部现有测试，确认净值和日报原有功能不回归。

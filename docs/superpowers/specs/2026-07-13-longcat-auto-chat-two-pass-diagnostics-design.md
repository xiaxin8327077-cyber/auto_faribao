# LongCat 自动聊天与两步诊断设计

## 目标

在现有 LongCat 企业微信助手上完成两项稳定性改造：

1. 无法匹配系统指令的普通问题自动进入聊天，不再要求用户添加“问助手”。
2. 线上诊断从多轮 Agent 改成“两步诊断”，减少模型往返和结构化输出波动。

现有日报、净值、定时任务、写操作确认和命令锁行为不变。

## 已选方案

### 普通问题自动聊天

路由结果增加 `chat` 类型。处理优先级保持为：

1. 现有确定性指令直接执行，不调用模型。
2. 未识别文本由 LongCat 路由为 `command`、`diagnose`、`chat` 或 `clarify`。
3. `chat` 使用现有 `AiChatService` 回答，并按用户保存最近 10 轮上下文。
4. `clarify` 只用于确实缺少操作参数或意图冲突的请求，不再承接普通知识问答。

保留 `问助手`、`进入助手模式` 和 `退出助手模式`，兼容现有使用习惯。自动聊天同样占用全局命令锁；有其他指令执行时不调用 LongCat。

未选方案：将所有未知文本直接交给聊天。该方案会绕过自然语言指令识别，无法区分“聊聊天”和“帮我把日报时间改到八点”。

## 两步诊断

### 第一步：规划

LongCat 只输出一次 JSON 计划，字段为 `tools`。计划最多包含 3 个只读工具调用，每项包含工具名和参数。系统执行以下校验：

- 工具名必须命中现有只读工具白名单。
- 参数必须是 JSON 对象。
- 重复工具调用去重。
- 超过 3 项时截断。
- 计划为空、JSON 非法或包含越权工具时安全失败，不执行任意命令。

### 批量取证

系统依次执行已校验的最多 3 个工具。工具仍由 `DiagnosticToolbox` 控制边界和脱敏，不能读取配置、密钥、Cookie、数据目录、备份或虚拟环境，也不能执行 Shell。

每项结果带工具名、成功状态和脱敏内容。单项失败不会阻止其他已规划工具执行。

### 第二步：报告

LongCat 接收原问题和批量取证结果，只生成一次 Markdown 报告，不再要求 JSON。报告必须包含：

- 原因或当前无法确定的说明。
- 至少一条诊断依据。
- 建议处理方式。
- 置信度。

系统在发送前再次脱敏并限制长度。报告为空、缺少依据、超时或模型失败时返回明确失败消息，不输出猜测。

未选方案：继续修复多轮 Agent JSON。LongCat 官方接口没有声明强制 JSON Schema 输出能力，多轮调用还会挤压 30 秒总时限。

## 时限与并发

- 总诊断时限仍为 30 秒。
- 规划阶段最多 10 秒。
- 工具执行共享剩余总时限。
- 报告阶段使用剩余时间，单次客户端上限 15 秒。
- 最多执行 3 个工具，低于原硬上限 8 次。
- 全过程与现有企业微信指令共用命令锁，并发固定为 1。

## 错误处理

- 普通聊天失败：释放命令锁并发送“AI助手暂时无法回答”。
- 规划 JSON 非法：诊断结束，不执行工具。
- 工具失败：把失败类型作为证据状态交给报告阶段，不泄露异常详情。
- 报告失败：释放命令锁并发送“线上诊断未完成”。
- 所有失败均不影响日报、净值、定时任务及网页功能。

## 测试与验收

- 精确指令仍不调用 LongCat。
- 普通知识问题路由为 `chat`，并通过现有聊天服务回答。
- 模糊写操作仍返回 `clarify` 或标准写指令，不能误执行。
- 写操作仍需“确认执行”。
- 有进行中指令时，自动聊天和诊断均不调用模型。
- 诊断只进行一次规划模型调用和一次报告模型调用。
- 最多执行 3 个白名单工具，越权工具被拒绝。
- 报告无需 JSON，输出再次脱敏且包含诊断依据。
- 完整测试、编译、服务健康和生产哈希校验通过后部署。
